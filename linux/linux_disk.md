## ディスク使用量の確認
* `df` … ファイルシステム単位のディスク容量の使用状況を表示する。「どこが逼迫しているか」を先に把握するために使う。
    * `df -h`（`-H` はSI単位系での表示） … 単位を付けて表示
    * `-a` 容量が0のファイルシステムも表示
    * `-T`（`--print-type`） 各ファイルシステムの種類を合わせて表示
    * `-i`（`--inodes`） ブロック使用量の代わりにiノード情報を表示。ファイル数が多い場合、容量に余裕があってもiノードが枯渇して書き込めなくなることがある。
* `du` … ファイル・ディレクトリ単位のディスク使用量を集計する。「どのディレクトリが容量を食っているか」を掘り下げるために使う。
* まず `df` で逼迫しているファイルシステムを特定し、次に `du` でその中のどこが原因かを絞り込む、という順序で使うのがよい。
* duの例
    * `du -sh ./storage/`
        * `-s` ディレクトリの総計を表示 / `-h` 単位を付ける
    * `du -sh ./storage/*`
        * ワイルドカードを付けると配下のファイル・ディレクトリごとに総計を表示する。ただしこれだと隠しファイル（`.` で始まるもの）が対象にならない。
    * `du -h --max-depth=1 ./storage/`
        * (IMO) 隠しファイルも含まれるうえ階層を制御できるため、これが一番使いやすい。`-a` を付けるとディレクトリだけでなくファイルの容量も表示される。
    * `du -sh /* -x | sort -nr`
        * ルート（`/`）に対して実行すると、外付けHDDなどをマウントしている場合に非常に時間がかかる。`-x` で別のファイルシステムのディレクトリを除外する。
    * `-b` バイト単位で表示する
        * `11G` のような表示だと、それが11GiBなのか11GBなのか区別が付かない。厳密に比較したい場合はバイト表示の方が分かりやすい。

## ディスクの圧迫
* ログローテーションは必ず設定しておく。
* (IME) エラー発生時にpostfixが `/var/mail` 配下にメールを溜め込み、それがディスクを圧迫していたケースがあった。アプリケーションのログだけでなく、こうした「意図せず溜まる場所」も監視対象に含めておく必要がある。
* ディスク容量不足はアプリケーションレベルでは直接検知しづらく、AWSのCloudWatchでも標準のメトリクスには含まれない（CloudWatch Agentを導入すれば取得できる）。何らかの仕組みで定期的にチェックしてアラートを出す対策をしておいた方がよい。

## ディスク速度の測定（dd）
* `dd` で簡易的な書き込み速度を測定できる（Dockerコンテナ内からホストへのアクセス速度の確認など）。
```
time dd if=/dev/zero of=test bs=1k count=100000
```
* `if=ファイル` … 標準入力の代わりにファイルから読み出す。デバイスファイルも指定可能
* `of=ファイル` … 標準出力の代わりにファイルへ書き込む。デバイスファイルも指定可能
* `bs=バイト数` … 1回に読み書きするブロックサイズ
* `count=個数` … 指定したサイズのブロックを個数分だけコピーする
* `/dev/zero` について
    * Unix系OSにおけるスペシャルファイルの1つで、全てヌル文字（ASCIIのNUL、`0x00`）の内容を読み出すことができる。
    * `/dev/null` と同じように、出力先として使うこともできる（`/dev/zero` への書き込みは何の効果ももたらさない）。
* **`dd` は書き込み先を間違えるとディスクの内容を破壊する。** 特に `of=` にデバイスファイル（`/dev/sda` など）を指定すると、そのパーティション・ディスクの全データが失われる。実行前に必ず `of=` の値を確認すること。
    * なお、`/dev/zero` の書き込みによるデータ消去は、政府・業界規格の一部では完全消去として認められない場合がある。
* より本格的に測定したい場合は `fio` コマンドを使う。
    * (参考) https://qiita.com/toshihirock/items/fa4d310115e6921ab0ac

## ファイルシステム
* (参考) https://qiita.com/kamihork/items/fbcd116a631324aae05d
* ファイルシステムとは
    * 記憶装置に保存されたデータを管理し、操作するために必要なOSの機能。
    * ファイルシステムがないと、データを読み出す際に「何番目のセクタ（ディスク区間）を取ってきて」のような指示をしなければならない。
    * 主に扱う観点としては、スケーラビリティ、ジャーナル（変更記録情報）による整合性、パフォーマンスなどがある。
    * 具体的には「データとメタデータをある構造に従ってストレージデバイス上に格納したもの」を指す。
* VFS（仮想ファイルシステム）
    * Linuxにおいて、ファイルシステムを統一的に操作するためのインターフェース層。
    * ファイルシステムごとの細かな違いを意識することなく、共通の方法でファイルやディレクトリに対する基本的な操作を行うことができる。
* ファイルシステムの構造
    * ブートブロック
        * OSを起動する情報を保存するブロック。常に先頭に位置する。
    * スーパーブロック
        * ブートブロックの直後に位置する領域。iノードテーブルのサイズ、論理ブロックサイズ、論理ブロック数などを保存する。
    * iノードテーブル
        * ファイルシステム内の全てのディレクトリ・ファイルが、それぞれ1エントリを占める。
    * データブロック
        * ファイルシステムの大半を占めるブロックで、ファイル・ディレクトリの実データを保持する。

### iノード
* iノード（index node）はファイルシステムにおけるデータ構造で、1ファイル・1ディレクトリごとに1エントリが使用される。
* iノード内には以下のような情報が保存され、それぞれにiナンバというユニークな識別番号が付与される。
    * ファイルの長さ（バイト数）
    * デバイスID（ファイルを格納しているデバイスを識別）
    * ファイル所有者のユーザーID、グループID
    * ファイルシステム内でファイルを識別するinode番号
    * ファイルモード（パーミッション）
    * 最終inode更新時（ctime）、最終ファイル更新時（mtime）、最終参照時（atime）のタイムスタンプ
    * そのinodeを指すハードリンクがいくつあるかを示す参照カウント
* iノードはファイルの属性を管理するが、ファイル名は含まれない。ファイル名はディレクトリエントリ側で管理されている。

### mount
* ファイルシステムを指定したディレクトリ（マウントポイント）と結びつけてアクセスできるようにする操作。
* HDD等の固定デバイスについては、システム起動時に自動的にマウントするよう設定されているのが通常。`/etc/fstab` に設定を記述することで実現する。
```
/dev/sdb5 /mnt/diskA ext4 defaults 0 0
```
* アンマウントできない場合、そのパス配下を使っているプロセスが残っている。[lsof](./linux_network.md) で確認できる。

### ボリューム・LVM
* ボリューム
    * 1個のファイルシステムを含むストレージ上の領域。
    * 厳密にはボリュームとパーティションは異なる。例えば1枚のフロッピーディスクは1個のボリュームだが、パーティションは存在しない。
* LVM（論理ボリュームマネージャ）
    * 物理ボリューム（ハードディスク等のストレージデバイス）に直接ファイルシステムをマップするのではなく、一旦「論理ボリューム」と呼ばれる仮想化されたボリュームに束ねて利用するためのシステム。
    * 複数のハードディスクやパーティションにまたがった記憶領域をまとめて、単一の論理ボリューム（LV）として扱える。
    * 利用者からは通常のパーティションと同様に見え、作成されたLVを個々に任意のフォーマットで利用できる。また、システムを停止せずに論理ボリュームのサイズを増減できる。
    * LVMがないと、最初に決めたパーティションサイズを後から変更するのにシステムの停止が必要になる。
    * (参考) https://www.pmi-sfbac.org/linux-lvm/
* 全体の関係の整理
    * ディスクを区切った各区画がパーティション。各パーティション（または論理ボリューム）上にファイルシステムを作成し、それをディレクトリにマウントして使う。ボリュームは「1個のファイルシステムを含む領域」を指す用語で、パーティションと重なるが同義ではない。LVMを使う場合は、パーティションに直接マップせず、仮想化された論理ボリュームを介して管理する。

### ファイルシステムの種類
* ext2（second extended filesystem）
    * 最大ファイルサイズ2TiB、最大ボリュームサイズ16TiB。ジャーナルには非対応のため、現在使う理由はない。
* ext3
    * ext2との高い互換性があり、ext2からの変換も可能。大きな変更点はジャーナルの追加。
* ext4
    * ext3の拡張で、Linuxのファイルシステムとして長く標準的に使われてきた。
    * 最大ファイルサイズは16TiB、最大ボリュームサイズは1EiB。ext3としてマウントすることもできる下位互換性を持つ。
    * Debian系のディストリビューションでは現在も既定として使われることが多い。
* XFS
    * Silicon Graphics社で設計されたファイルシステム。最も古いジャーナリングファイルシステムの一つ。
    * マウントした状態でのデフラグなどの操作が可能。最大ファイルサイズ8EiB、最大ボリュームサイズ8EiB。
    * 当初からハイエンドシステム向けに開発されたため、スケーラビリティの面でext4を上回る。RHEL 7以降で既定のファイルシステムに採用されているのはそうした理由による。
* JFS
    * 「Journaled File System」の略で、IBMが自社の商用UNIXであるAIXに採用したファイルシステム。
    * 最大ファイルサイズ4PiB、最大ボリュームサイズ32PiB。信頼性は高いが、ディストリビューションの既定として選ばれることはほとんどない。
* Btrfs、ZFS
    * スナップショット、チェックサムによる整合性検証、圧縮などの機能を持つ、より新しい世代のファイルシステム。openSUSEはBtrfsを既定としており、Ubuntuなどでも選択できる(?)。
* FAT / FAT32
    * 「File Allocation Table」の略で、古いWindowsで使用されていたファイルシステム。
    * ジャーナルに非対応でスケーラビリティも貧弱。またLinuxのパーミッション情報などの属性を引き継げない。
    * FATの最大ファイルサイズ・最大ボリュームサイズは4GiB。FAT32はその32ビット版で、扱えるボリュームサイズが大きくなっている（ファイルサイズの上限は4GiBのまま）。
    * 古典的であるがゆえに大半のOSで読み書きが可能なので、外付けメディアの受け渡し用として今も使われる。

## dfコマンドでの確認
* `df` はマウントしているファイルシステムを表示する。
* `df -T` でファイルシステムの種類を確認できる。
* `tmpfs`
    * メモリ上に確保される一時ファイル用のファイルシステム。再起動で消えるため、通常は気にしなくてよい。
* 出力の読み方の例
    * `sda1` は通常のパーティションで `/boot` にマウントされている。
    * `sda2` はLVMで管理されるパーティションで、その中に論理ボリューム（`centos-root` と `centos-swap` など）がある。それぞれ `/` とswapに使われている。
    * swap領域はマウントされているわけではないため、使用状況は `df` ではなく `swapon -s`（もしくは `swapon --show`）で確認する。

## Linuxにおけるデバイス名
* Linuxにおけるディスクおよびパーティションの命名法は、他のOSとは異なる。パーティションを作成したりマウントしたりする際には、Linuxがどのようなディスク名を用いるのか知っておく必要がある。
    * 第1フロッピードライブは `/dev/fd0`、第2は `/dev/fd1`
    * 最初に見つかったハードディスクは `/dev/sda`、2番目は `/dev/sdb`、以下同様
    * 第1 SCSI CD-ROMは `/dev/scd0` および `/dev/sr0`
    * NVMe SSDの場合は `/dev/nvme0n1`、そのパーティションは `/dev/nvme0n1p1` のような命名になる。
* 各ディスクのパーティションは、ディスク名に十進数を付け加えることで表す。例えば `sda1` と `sda2` は、それぞれ第1ディスクの第1、第2パーティションを表す。
* Windowsのようなドライブレター（`C:` 等）の概念はなく、パーティションを任意のディレクトリにマウントして使用する。
* SCSI（Small Computer System Interface）
    * コンピュータ本体にストレージ装置などの周辺機器を繋いで通信するための接続方式の標準規格の一つ。`sd` という接頭辞はこれに由来するが、現在はSATAやUSB接続のディスクも同じ命名規則で扱われる。

## パーティション
* (参考) https://eng-entrance.com/linux-partition
* パーティションとは、OSに関係なくPCの記憶媒体（HDD、SSD、メモリスティック等）に設けることができる「仕切り」のこと。もう一台別の記憶媒体を認識させているかのように扱うことができる。
* パーティション設定は、インストールやセットアップ段階で設定した後の変更が難しい（不可能ではないが推奨されない）。計画性をもって設定する必要がある。
    * ただしLVMを使っていれば、後からのサイズ変更は比較的容易になる。
* パーティションを分けるメリット
    * システム領域とデータ領域を分離できる。システムリカバリ時に、システム領域だけを初期化してデータを保持・引き継ぎできる。
    * Linuxの場合は `/` と `/home` を分けてこれを実現することが多い。`/home` はユーザーごとのデータ保存領域。
    * swapパーティションも重要。メインメモリが不足しているときに、その代わりとして使用できる領域。
* パーティションの種類
    * BIOS + MBR（Master Boot Record）による管理の場合、基本パーティションは4つまでしか作成できない。それ以上細かく分けるには、拡張パーティションという特殊領域を確保し、その中に論理パーティションを作る。
        * BIOS … ファームウェアの一つで、ハードウェアとの最も低レベルの入出力を行うプログラム。電源投入と同時に実行される。
        * MBR … 単数または複数のパーティションに分けられたディスクの、パーティション外に存在する先頭セクタ。サイズは512バイト。
        * MBRで管理できるディスク容量の上限は2TB。
    * UEFI（Unified Extensible Firmware Interface）+ GPT（GUID Partition Table）の場合、一般的に128個のパーティションを設定でき、論理パーティションや拡張パーティションを考える必要がない。管理できる最大容量も大幅に拡張されている。
    * 現在の環境では UEFI + GPT が標準と考えてよい。
* パーティション設計の目安（100GB程度のディスクを前提とした例）
    * `/boot` … 500MB〜1GB程度（UEFI環境ではEFIシステムパーティションも別途必要）
    * `/` … 20GB程度
    * `/usr` … ライブラリおよびプログラムバイナリがほぼここにインストールされるため、多めに見積もる
    * `/var` … 5GB程度。ログなど細々としたものが多く置かれる
    * `/home` … データを大量に保持する場合、残りの容量を割り当てる
    * swap … メインメモリと同程度が一般的。メインメモリを十分に搭載しているなら、それ以上のスワップ領域を設定しても期待するパフォーマンスは得られない。倍のスワップ領域が必要になるような状態なら、メモリの増設を検討する方が妥当
    * (?) 現在はクラウド上の仮想マシンやコンテナが中心で、細かくパーティションを切る機会自体が減っている。
* ディレクトリごとの役割は[ディレクトリ構造](./linux_directory.md)を参照。

### パーティションの作成手順
* `fdisk` コマンドでパーティションを設定できる。**間違えると取り返しがつかないコマンド**なので、まずは仮想マシンなどで試すのがよい。
```
# fdisk /dev/sdb   # 対話的にパーティションの作成や削除ができる（sdbは例として接続したUSBメモリ）
```
* フォーマット
```
mkfs.ext4 /dev/sdb1   # ext4の場合
mkfs.xfs /dev/sdb1    # XFSの場合
```
* マウント
```
mount /dev/sdb1 /mnt
```
* 確認
```
df -T
```
* マウント解除
```
umount /mnt/
```
    * Windowsでいう「ハードウェアを安全に取り外す」に該当する。USBメモリなどをマウントしたら、抜く前に必ず `umount` すること。umountせずに引き抜くと、ファイルシステムの破損につながる。
